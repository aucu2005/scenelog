2. 배포란 무엇인가 — "제 컴퓨터에서는 돌아요"를 끝내는 일

지금까지 앱은 내 컴퓨터에서만 살아 있었다. 내가 꺼지면 앱도 꺼지고, 다른 사람은 접속할 방법이 없다. 요리 비유로: 레시피(코드)와 시식 평가(측정 숫자)는 있는데 식당이 없어서 아무도 와서 먹어볼 수 없는 상태.

배포(deploy)는 식당 문을 여는 일이다. 구체적으로는:

  1. 항상 켜져 있는 컴퓨터를 빌린다 → EC2
  2. 거기서 내 앱을 돌린다 → Docker 컨테이너
  3. 인터넷의 누구나 찾아올 수 있는 주소를 단다 → 공인 IP (+ 고정시키려면 Elastic IP)
  4. 들어올 문과 잠글 문을 정한다 → 보안그룹

이 네 가지가 오늘 한 일의 전부다. 나머지는 전부 이 넷을 안전하고 재현 가능하게 만드는 장치다.

3. 컨테이너화 — 앱을 "어디서나 똑같이 도는 상자"에 담기

왜 EC2에서 gradlew bootRun을 안 하나?

로컬에서는 IDE가 Java 17, 환경변수, 포트를 다 챙겨줬다. EC2는 맨몸의 리눅스다 — Java 설치, 버전 맞추기, 서비스 등록을 손으로 하면 "내 PC와 서버가 미묘하게 다른" 문제가 평생 따라다닌다. 컨테이너는 앱과 실행 환경(JRE까지)을 통째로 상자에 담아 이 문제를 없앤다. 이삿짐 비유: 가구를 낱개로 옮기면(수동 설치) 뭔가 빠지지만, 컨테이너째 옮기면 그대로다.

Dockerfile 멀티스테이지 — 주방과 도시락

😰 나쁜 예 — 한 단계로 다 넣기 
FROM eclipse-temurin:17-jdk      # JDK + gradle + 소스 + 빌드 부산물 전부 포함
COPY . .
RUN ./gradlew bootJar
CMD java -jar build/libs/app.jar # 이미지 ≈ 1GB. 소스코드도 들어 있다
✅ 우리 구조 — 빌드 주방과 배달 도시락을 분리 (실제 Dockerfile) 
# ── 1단계: 빌드 (주방 — JDK, gradle, 소스가 다 있다)
FROM eclipse-temurin:17-jdk AS build
COPY src ./src
RUN ./gradlew bootJar -x test --no-daemon

# ── 2단계: 실행 (도시락 — 완성된 jar와 JRE만)
FROM eclipse-temurin:17-jre-alpine
COPY --from=build /app/build/libs/*.jar app.jar   # 주방에서 jar만 꺼내온다
ENTRYPOINT ["java", "-jar", "app.jar"]

2단계 이미지에는 gradle도 소스도 JDK도 없다 — 작고(≈200MB), 공격 표면이 좁다. -x test는 테스트 제외: 테스트는 DB가 필요해서 이미지 빌드 중에는 돌 수 없다 (로컬·CI 몫).

디테일 두 개:

  • sed -i 's/\r$//' gradlew — Windows에서 만든 파일의 CRLF 줄바꿈이 리눅스 sh를 깨뜨린다. 항상 정규화.
  • .dockerignore — build/·.git·docs를 빌드 컨텍스트에서 제외. 이미지에 불필요한 것이 새어들지 않는다.

compose profile — 한 파일, 두 용도

😰 나쁜 예 docker-compose.yml(로컬용)과 docker-compose.prod.yml(배포용) 두 벌 관리 — 반드시 어긋난다. ✅ 우리 구조 한 파일에 profile로 스위치를 단다:

services:
  app:
    profiles: ["app"]     # ← 이 한 줄이 스위치
docker compose up -d                       # DB 3개만 (로컬 개발 — 앱은 IDE로)
docker compose --profile app up -d --build # 앱 포함 4개 (EC2 배포)

로컬 개발 흐름은 그대로 두고, 배포 때만 app이 켜진다. 배포와 로컬이 같은 파일을 쓰므로 "로컬에선 됐는데 배포 구성이 달라서" 류의 버그가 원천 차단된다.

localhost의 함정 — 컨테이너 안에서 localhost는 자기 자신이다

    environment:
      POSTGRES_HOST: postgres   # ✅ 서비스명 — compose가 만들어주는 내부 DNS
      # POSTGRES_HOST: localhost ❌ 앱 컨테이너 자신 → DB 없음 → 접속 실패

아파트 비유: 로컬에서는 앱과 DB가 한 집에 살아서 "우리 집(localhost)"이 통했다. 컨테이너는 각자 다른 호(戶)다 — 옆집을 부르려면 호수(서비스명)를 불러야 한다. day1에 ${POSTGRES_HOST:localhost}로 설계해 둔 덕에 코드 수정 없이 환경변수만 바꿔 끼웠다.

4. Terraform — 인프라를 클릭이 아니라 코드로

나쁜 예 vs 우리 구조

😰 콘솔 클릭 40번

EC2 콘솔 로그인 → 인스턴스 시작 → AMI 고르고 → 타입 고르고 → 보안그룹 만들고 → 규칙 넣고… 다 만들고 나면 무엇을 어떻게 만들었는지 기록이 없다. 실수로 지우면? 처음부터 다시 클릭. 면접에서 "어떻게 구성했어요?" → "어… 클릭해서…"

✅ 코드 (실제 infra/main.tf) 
resource "aws_instance" "scenelog" {
  ami           = data.aws_ssm_parameter.al2023.value  # 항상 최신 AL2023
  instance_type = "t3.micro"                           # RAM 1GB
  key_name      = var.key_name
  vpc_security_group_ids = [aws_security_group.scenelog.id]
}

인프라 전체가 118줄 파일 하나다. 지워져도 terraform apply 한 번이면 동일하게 재생성되고, 저장소에 커밋되어 "이렇게 구성했습니다"의 증거가 된다. 이것이 IaC(Infrastructure as Code)다.

plan → apply 2단계 — 미리보기 없이 실행하지 않는다

terraform plan   →  "생성 2개, 변경 0, 삭제 0"   ← 무슨 일이 일어날지 미리 보여준다
terraform apply  →  실제 실행 (13초 만에 인스턴스 생성)

DB의 트랜잭션 미리보기 같은 것. 특히 삭제가 0인지를 plan에서 확인하는 습관이 사고를 막는다. 상태 파일(terraform.tfstate)은 "현재 AWS에 뭐가 있는지"의 장부 — IP 등 상세가 담기므로 커밋 금지(.gitignore).

user_data — 서버의 "입주 전 청소 목록"

인스턴스가 처음 켜질 때 한 번 실행되는 스크립트. 우리는 여기에 부팅 준비를 전부 자동화했다:

# infra/main.tf의 user_data (요약)
dd if=/dev/zero of=/swapfile bs=1M count=2048 && swapon /swapfile  # ① swap 2GB
dnf install -y docker git && systemctl enable --now docker         # ② Docker
curl -SL .../docker-compose-linux-x86_64 -o .../docker-compose     # ③ compose 플러그인
git clone https://github.com/aucu2005/scenelog.git                 # ④ 저장소

SSH로 들어가서 명령을 타이핑하는 것과 결과는 같지만, 사람이 개입할 틈이 없어 빠뜨릴 수도 없다. 단, 여기에 시크릿은 절대 넣지 않는다 — user_data는 콘솔에서 평문으로 조회된다 (§6).

5. EC2 낱말 사전 — 오늘 나온 이름들

용어비유우리 값
EC2 인스턴스시간 단위로 빌리는 컴퓨터t3.micro (vCPU 2 · RAM 1GB)
AMIOS 설치 USB — 어떤 리눅스로 시작할지Amazon Linux 2023 (SSM 파라미터로 최신 자동 선택)
키페어현관 열쇠 — 공개키는 서버에, 개인키(.pem)는 내 PC에devmatch-key 재사용
보안그룹공동현관 경비 — 어느 문으로 누가 들어올 수 있나8080 전체 공개 · 22 내 IP만 · 나머지 전부 봉인
공인 IP임대 전화번호 — 껐다 켜면 다른 번호(처음 54.180.30.61이었다)
Elastic IP내가 소유한 전화번호 — 기기를 바꿔도 유지13.124.60.61 (고정)

SSH — 열쇠로 원격 터미널 열기

ssh -i ~/.ssh/devmatch-key.pem ec2-user@13.124.60.61

비밀번호가 아니라 개인키 파일로 인증한다. 서버에는 짝이 되는 공개키만 있어서, 서버가 털려도 내 개인키는 유출되지 않는다. 개인키 파일은 절대 커밋·전송하지 않는다.

Elastic IP를 붙인 이유 (배포 다음 날 결정)

기본 공인 IP는 인스턴스를 중지(stop)하면 반납된다 — 다시 켜면 새 번호. 서류에 URL을 적는 순간 그 주소는 몇 주간 불변이어야 하므로, 계정 소유의 고정 IP로 바꿨다:

resource "aws_eip" "scenelog" {
  instance = aws_instance.scenelog.id   # 이 인스턴스에 고정 번호를 붙인다
  domain   = "vpc"
}

비용 구조가 재밌다: 켜진 인스턴스에 붙어 있으면 추가 비용 없음, 잡아두고 안 쓰면 시간당 $0.005 — IPv4가 고갈 자원이라 "낭비하지 말라"는 인센티브다.

6. 보안 — 연 문과 잠근 문

최소 개방 원칙

8080 (앱)    → 0.0.0.0/0 (전 세계)   ← 이것이 오늘의 목적이므로 연다
22   (SSH)   → 내 IP/32 하나만       ← 관리용. 전 세계에 열면 몇 분 안에 봇이 두드린다
5432 / 27017 / 6379 (DB들) → 아예 안 연다  ← 규칙 자체가 없음 = 존재를 모른다

DB 포트를 안 여는 근거: DB는 같은 호스트의 앱 컨테이너만 쓰면 된다. 외부에서 직접 접속할 이유가 하나도 없으므로 문을 만들지 않는 것이 최선의 방어다. (참고: 인터넷에 열린 MongoDB는 스캐너가 몇 시간 안에 찾아내 랜섬 노트를 남기는 게 현실이다.)

시크릿 3원칙 (오늘 실제로 지킨 것)

  1. 커밋 금지 — .env는 .gitignore. 저장소는 public이다
  2. 환경마다 다른 값 — EC2의 DB 비밀번호·JWT 시크릿은 로컬과 다른 무작위 값으로 새로 생성 (로컬이 유출돼도 서버는 안전, 그 역도 성립)
  3. 전달 경로도 가린다 — user_data(콘솔 평문 노출)가 아니라 SSH 표준입력으로만 전달. 화면·로그 어디에도 값이 찍히지 않았다

7. 메모리와의 싸움 — 1GB에 4개 컨테이너 넣기

예산표

t3.micro의 RAM 1GB는 넉넉하지 않다. 기본값대로 올리면 JVM 혼자 600MB를 집는다:

컨테이너방치하면우리가 정한 상한
Spring Boot400~600MB힙 -Xmx384m, 컨테이너 mem_limit 640m
MongoDB250MB+ (RAM에 비례해 증가)WiredTiger 캐시 0.25GB, mem_limit 384m
PostgreSQL150~250MBmem_limit 256m
Redis무제한 (기본값!)maxmemory 64mb + LRU 축출, mem_limit 96m

OOM Killer가 무서운 이유

메모리가 바닥나면 리눅스 커널이 가장 큰 프로세스를 조용히 죽인다. 자바 예외도, 앱 로그도 없다 — 프로세스가 밖에서 살해되기 때문이다. 증거는 커널 로그에만 남는다: dmesg | grep -i "killed process".

4겹 선제 대응 → OOM 0회

① swap 2GB       — user_data에서 부팅 시 자동 (RAM이 넘치면 디스크로 흘려보낼 완충지)
② JVM 힙 상한     — day1 compose 설계 때부터
③ 컨테이너별 상한  — 한 놈이 폭주해도 이웃을 못 죽인다
④ 로컬 사전 검증   — 같은 제약의 compose로 로컬에서 미리 4개를 띄워봤다

결과: 빌드·ETL·시뮬·집계 전 과정 OOM 0회. dmesg 빈 출력이 증거다. 계획서는 "거의 확실히 만난다"고 했지만 — 장애 대응만 경험이 아니다. 예방 성공도 실측(free/dmesg/docker stats)으로 남기면 증거가 된다 (트러블슈팅 7호).

8. 배포 검증 — 안에서 밖으로, 그리고 상태 의존성

검증은 동심원 순서로

① 컨테이너:  docker ps → 4개 전부 (healthy)
② 호스트:    EC2 안에서 curl localhost:8080/actuator/health
③ 외부:      내 PC 브라우저에서 http://13.124.60.61:8080 → UP     ← 이것만이 "배포됐다"의 증거
④ 데이터:    ETL → 시뮬 → 집계 → 타임라인/하이라이트 응답 확인

①이 되고 ③이 안 되면 보안그룹 문제, ③이 되고 ④가 비면 데이터 문제 — 원 단위로 잘라야 어디가 끊겼는지 즉시 안다.

오늘 실제로 겪은 문제 2건 (트러블슈팅 7호)

① clone 시점과 push 시점의 어긋남 — user_data가 저장소를 clone한 시점은 Dockerfile을 push하기 전이었다. 자동화(clone)와 수동 작업(push)의 순서 의존성을 놓친 것. 이후 재배포 절차를 git pull &&로 시작하게 통일했다.

② EC2에서만 터진 signup 400 — 원인은 nickname 필드 누락. 로컬에서는 계정이 예전에 만들어져 있어서 이 경로를 오래 안 탔다.

"로컬에서 되던 것"에는 로컬에 쌓인 상태가 포함돼 있다. 깨끗한 환경에 배포하는 순간 상태 의존이 전부 드러난다. 첫 배포는 기능 테스트가 아니라 상태 의존성 테스트다.

번외 — 같은 날 로컬에서도 한 건: 문서의 IP를 PowerShell로 일괄 치환했다가 한글이 전부 깨졌다. PowerShell 5.1은 BOM 없는 UTF-8을 CP949로 오독한다. git으로 복원하고, ASCII 문자열 치환은 바이트 단위로 안전한 sed로 다시 했다. 인코딩을 모르는 도구에 한글 파일을 맡기지 말 것.

9. 면접 예상 질문과 답

Q1. "배포를 어떻게 하셨나요?"

앱을 멀티스테이지 Dockerfile로 컨테이너화하고, EC2 t3.micro에 docker compose로 올렸습니다. 인프라(보안그룹·EC2·Elastic IP)는 Terraform 코드로 정의해 재현 가능하게 했고, 부팅 준비(swap·Docker 설치·clone)는 user_data로 자동화했습니다.

Q2. "RAM 1GB에 컨테이너 4개면 부족하지 않나요?"

부족합니다. 그래서 층마다 상한을 걸었습니다 — JVM 힙 384MB, 컨테이너별 mem_limit, Mongo WiredTiger 캐시 0.25GB, Redis 64MB LRU, 그리고 swap 2GB를 부팅 시 자동 생성. 로컬에서 같은 제약으로 사전 검증까지 해서 배포 전 과정 OOM 0회였고, dmesg로 실측 확인했습니다.

Q3. "DB 포트는 왜 안 열었나요?"

DB는 같은 호스트의 앱만 사용하므로 외부에서 접속할 이유가 없습니다. 보안그룹에 규칙 자체를 만들지 않는 것이 가장 확실한 방어라고 판단했습니다. 관리용 SSH도 제 IP 하나로만 제한했습니다.

Q4. "Terraform을 왜 썼나요?"

콘솔 클릭은 기록이 남지 않고 재현이 안 됩니다. 코드로 정의하면 저장소가 곧 인프라 문서가 되고, 같은 환경을 몇 번이든 다시 만들 수 있습니다. plan으로 변경 사항을 미리 확인하고 apply하는 2단계도 사고 예방에 유효했습니다.

Q5. "Elastic IP는 왜 붙였나요?"

기본 공인 IP는 인스턴스를 중지하면 반납되어 주소가 바뀝니다. 서류에 적는 URL은 심사 기간 내내 불변이어야 하므로 계정 소유의 고정 IP를 붙였습니다. 켜진 인스턴스에 연결된 동안은 추가 비용이 없다는 것도 확인했습니다.
