## 1. 오늘 만든 것 — 한 장 그림

```
reaction_events (MongoDB, 1,883건)          ← 원본: "누가 몇 초에 뭘 눌렀나" 점 1,883개
        │
        │  Aggregator.aggregate(events, 10)
        ▼
segment_stats (PostgreSQL, 820행)           ← 집계: 10초 버킷별 반응 수
        │
        │  HighlightDetector.detect(totals, 10)
        ▼
highlights (PostgreSQL, 2행)                ← 검출: "유별나게 높은 구간" 2개
        │
        │  GET /api/contents/1/timeline
        ▼
Redis 캐시 (scenelog:timeline::1)           ← 조회: 두 번째부터는 DB 안 감
```

실측 결과:

| 항목 | 값 |
|---|---|
| **정답지 채점** | 심은 피크 2개 중 **2개 검출 (100%)** — 2800~2860s(정답 2802~2852) · 7050~7120s(정답 7058~7118) |
| 멱등 | 집계 2회 실행 → 버킷 820·하이라이트 2 동일 |
| 캐시 | 미스 516ms → 히트 **p50 22.4ms** (~23배) |

## 2. 집계 — 왜 미리 뭉쳐 두는가 (fact와 mart)

### 나쁜 예 vs 우리 구조

**😰 조회할 때마다 계산:**
```java
// 타임라인 요청이 올 때마다 원본 1,883건(나중엔 100만 건)을 읽어 그 자리에서 집계
GET /timeline → find 1,883 events → group by bucket → 응답
```
사용자가 늘수록, 데이터가 쌓일수록 조회가 느려진다. 같은 계산을 요청마다 반복한다.

**✅ 우리 구조 — 계산은 배치가, 조회는 읽기만:**
```
쓰기 시점(가끔):  aggregate 실행 → 820행으로 미리 요약해 저장
읽기 시점(자주):  segment_stats 820행을 그냥 읽는다 (계산 0)
```

이것이 데이터 웨어하우스 용어로 **fact(원본) / mart(요약)** 분리다.
`reaction_events`가 fact, `segment_stats`가 mart — 공고 담당업무 6("데이터 웨어하우스/마트 설계")의 축소판.

### 버킷 계산 한 줄

```java
int bucketStart = (e.offsetSec() / bucketSizeSec) * bucketSizeSec;
// 2431 / 10 * 10 = 2430   (정수 나눗셈이 나머지를 버린다)
// 2440 / 10 * 10 = 2440   (경계값은 자기 버킷 — 테스트로 못박음)
```

`Aggregator`는 **순수 함수**다 — 같은 입력이면 항상 같은 출력. 이 성질이 뒤의 멱등을 만든다.

## 3. 검출 — z-score는 "얼마나 유별난가"의 숫자

"AI"가 아니다. 고등학교 통계다. 정직하게 표현하는 것이 오히려 강하다.

### 3단계 알고리즘 (`HighlightDetector`)

**① 이동평균 — 한 버킷짜리 우연한 튐을 완만하게**
```java
// 창 크기 3: 각 버킷을 이웃과 평균 낸다
[4, 5, 60, 5, 4]  →  [4.5, 23, 23.3, 23, 4.5]
// 진짜 피크는 이웃도 높아서 살아남고, 외톨이 튐은 희석된다
```

**② z-score — 평균에서 몇 표준편차 떨어졌나**
```java
double z = (smoothed[k] - mean) / std;
// z = 0  → 평범           z = 2  → 상위 약 2% 수준으로 유별남 (우리 임계값)
// z = 11.76 → 오늘 검출된 TENSION 피크. 압도적으로 유별남
```

**③ 연속 병합 — z ≥ 2.0인 버킷이 이어지면 하나의 "구간"으로**
```
버킷:  2800  2810  2820  2830  2840  2850
z:      2.3   5.1  11.7   9.2   4.4   2.1   → 하나의 구간 2800~2860 (score = 최대 z)
```

### 오늘의 발견 — 테스트가 가르쳐준 통계

12버킷짜리 인공 데이터로 만든 테스트가 **실패**했다. 계산해 보니:

```
짧은 시계열에서는 피크 자신이 평균과 표준편차를 크게 부풀린다
→ (피크값 - 커진 평균) / 커진 σ = z가 오히려 작아짐 (실측 z=1.96 < 임계 2.0)

기준선을 20버킷으로 늘리면 → σ가 안정 → 같은 피크의 z=2.67 → 검출됨
```

**z-score는 기준선이 충분히 길어야 일한다.** 실데이터(820버킷)가 잘 되는 이유다.
알고리즘 버그가 아니라 통계의 성질 — 이걸 구분하는 것이 디버깅과 데이터 감각의 차이다.

### method 컬럼 — 알고리즘 버저닝

```java
public static final String METHOD_ZSCORE_V1 = "ZSCORE_V1";
// 삭제도 method 단위로만:
highlightRepository.deleteAllByContentIdAndMethod(contentId, METHOD_ZSCORE_V1);
```
나중에 더 좋은 검출법(V2)을 만들면 **V1 결과를 지우지 않고 나란히 저장해 비교**할 수 있다.
"어느 쪽이 나은가"를 데이터로 말할 수 있는 구조.

## 4. 멱등 — 전량 재계산, 그리고 delete를 먼저 하는 이유

### 증분 vs 전량 재계산

**😰 증분 (마지막 처리 지점을 기억):**
```
"지난번에 1500번 이벤트까지 처리했으니 이번엔 1501번부터"
→ 워터마크 저장 필요, 재실행하면 이중 계산 위험, 멱등 증명 어려움
```

**✅ 전량 재계산 (우리 선택):**
```java
segmentStatRepository.deleteAllByContentId(contentId);   // 다 지우고
segmentStatRepository.saveAll(...);                      // 처음부터 다시 넣는다 (한 트랜잭션)
```
느리지만 단순하고, **몇 번을 실행해도 결과가 같음이 자명**하다.
한계도 안다: 콘텐츠당 이벤트가 수백만 건이 되면 증분으로 전환해야 한다 — README 한계 절에 기록.

### 왜 UPSERT가 아니라 delete + insert인가 (미묘하지만 중요)

```
UPSERT만 쓰면: 지난 집계에 있던 버킷 2430이 이번 계산에 없으면? (이벤트가 지워진 경우)
              → 옛 행이 그대로 남는다. 결과가 원본과 어긋남.
delete+insert: 결과가 항상 "현재 원본의 정확한 요약"이다.
```
한 트랜잭션 안이므로 중간의 빈 상태는 밖에서 보이지 않는다.

## 5. 캐시 — 도입보다 무효화가 핵심

### 짝을 이루는 어노테이션 2개

```java
// TimelineService — 조회: 있으면 Redis에서, 없으면 DB에서 읽고 Redis에 저장
@Cacheable(value = "timeline", key = "#contentId")
public List<TimelineBucketResponse> timeline(Long contentId) { ... }

// AggregationService — 집계 완료: 해당 콘텐츠의 캐시를 지운다
@CacheEvict(value = "timeline", key = "#contentId")
public Map<String, Object> aggregate(Long contentId) { ... }
```

**😰 무효화 없는 캐시**는 "빠르게 옛날 데이터를 보여주는 장치"다. 집계가 갱신돼도 사용자는
10분(TTL) 동안 낡은 타임라인을 본다. TTL은 evict가 누락됐을 때의 **안전망**이지 주 무효화 수단이 아니다.

실측한 전체 사이클:
```
① 첫 조회(미스) 516ms → Redis에 scenelog:timeline::1 생성
② 20회 반복 조회(히트) p50 22.4ms / p95 39.5ms        ← ~23배
③ 집계 실행 → 키 삭제됨 (evict)
④ 재조회 → 키 재생성
```

### 왜 Caffeine(로컬)이 아니라 Redis인가

로컬 캐시는 그 프로세스 안에만 있다. 인스턴스가 2대가 되는 순간
"1번 서버는 새 데이터, 2번 서버는 옛 데이터"가 된다. 캐시를 프로세스 밖(Redis)에 두면
인스턴스가 늘어도 캐시는 하나다 — 지금은 1대지만, 확장 시 코드 변경이 없는 구조를 선택.

## 6. 트러블슈팅 5호 — "저장은 되는데 읽기만 500"

오늘 가장 값진 사고. 캐시 검증 중:

| 동작 | 결과 |
|---|---|
| 첫 조회 (저장) | ✅ 200, 키 생성 |
| **두 번째 조회 (히트=읽기)** | ❌ **500** |
| evict | ✅ 정상 |

### 원인 — record와 직렬화기의 궁합

```
GenericJackson2JsonRedisSerializer는 "무엇이든" 복원하려고 JSON에 @class 타입 정보를 심는다
그런데 심는 정책이 NON_FINAL — final이 아닌 클래스에만 심는다
record는 항상 final이다 → 타입 정보 없이 저장됨
읽을 때: "타입 id가 있어야 하는데?" → SerializationException → 500
```

**저장은 아무 검증 없이 성공하고 읽기에서만 터진다** — 캐시 미스 경로만 테스트하면 절대 못 잡는다.

### 해결 — 타입을 아는 캐시엔 타입 명시 직렬화기

```java
// RedisConfig — 값 타입이 List<TimelineBucketResponse>로 고정이므로 명시한다
var timelineType = mapper.getTypeFactory()
        .constructCollectionType(List.class, TimelineBucketResponse.class);
new Jackson2JsonRedisSerializer<>(mapper, timelineType)
// 타입 메타데이터가 아예 불필요 → JSON도 작고 깨끗해진다
```

**교훈: 캐시는 미스·히트·무효화 세 경로를 전부 검증한다.**

## 7. 부정 테스트 — "설정이 읽히는지 의심되면 틀린 값을 넣어보라"

Mongo 프리픽스가 조용히 무시된 사건(3호) 때문에 Redis 설정도 의심스러웠다. 검증법:

```
REDIS_HOST=bogus-redis-host 로 기동 → /actuator/health → 503 DOWN
```

값이 무시됐다면 기본값(localhost)으로 붙어 UP이 나왔을 것이다. **DOWN이 나온 것이 정상 바인딩의 증거.**
"성공해서 확인"은 기본값 덕분일 수 있지만, "틀린 값으로 실패"는 확실하다 — 부정 테스트의 힘.

## 8. 면접 예상 질문과 답

**Q1. "집계를 왜 미리 해두나요? 조회할 때 계산하면 안 되나요?"**
> 조회는 자주 일어나고 집계는 가끔 갱신됩니다. 요청마다 원본 수만~수백만 건을 훑는 대신,
> 배치가 한 번 계산해 요약 테이블에 저장하고 조회는 읽기만 하게 분리했습니다.
> 원본(fact)과 요약(mart)을 나누는 데이터 마트 설계의 축소판입니다.

**Q2. "하이라이트 검출에 AI를 쓰셨나요?"**
> 아니요, 통계입니다. 10초 버킷 반응 밀도에 이동평균을 적용하고 z-score 2.0 이상인 연속
> 구간을 검출합니다. 시뮬레이터에 정답 피크를 심어 채점했고 2개 중 2개를 찾았습니다.
> 통계 기반이라고 정직하게 표현하는 것이 맞다고 판단했습니다.

**Q3. "캐시 무효화는 어떻게 하나요?"**
> 집계가 완료되는 시점에 해당 콘텐츠의 캐시 키를 명시적으로 지웁니다(@CacheEvict).
> TTL 10분도 있지만 그건 evict가 누락됐을 때의 안전망입니다.
> 미스·히트·무효화 세 경로를 각각 검증했고, 히트에서만 터지는 직렬화 문제를 그 과정에서 잡았습니다.

**Q4. "전량 재계산이면 느리지 않나요?"**
> 지금 규모(콘텐츠당 수천~수만 건)에서는 문제없고, 멱등성 증명이 쉬운 쪽을 택했습니다.
> 콘텐츠당 이벤트가 수백만 건이 되면 워터마크 기반 증분으로 전환해야 한다는 한계를
> 문서에 남겼습니다.
