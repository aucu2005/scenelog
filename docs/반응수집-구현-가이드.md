## 1. 오늘 만든 것 — 한 장 그림

```
[시뮬레이터]                         [수집 API]                    [MongoDB]
Scenario(각본)                POST /api/sessions/{id}/reactions
 "27% 지점에 TENSION 피크"  →   검증 5종 통과해야만           →   reaction_events

      │
      └─ 정답지(answerPeaks)를 응답으로 공개
```

실측 결과:

| 항목 | 값 |
|---|---|
| 생성·적재 | 오디세이(10380초) × 20명 → **1,883건** |
| **재실행** | `inserted=0, skipped=1883` — **멱등 증명** |
| 정답지 | TENSION 2802~2852s / TOUCHED 7058~7118s |
| 검증 응답 | 남의 세션 **403** · offset 초과 **400** · 501건 배치 **400** · 없는 enum **400** · 없는 세션 **404** |

## 2. 왜 시뮬레이터인가 — 다시 한 번

프론트엔드(반응 버튼 UI)는 범위 밖이다. 그런데 백엔드 입장에서 보면:

```
[버튼 클릭] ──HTTP──> POST /api/sessions/17/reactions {"offsetSec":2431,"reactionType":"TENSION"}
[시뮬레이터] ─메서드 호출─> 같은 검증, 같은 저장 경로
```

**서버는 요청이 어디서 왔는지 구분하지 못하고, 구분할 필요도 없다.**
게다가 시뮬레이터는 실사용자가 못 주는 것을 준다 — **정답**. 어디에 피크를 심었는지 알기 때문에,
검출기가 그걸 찾아내는지 **채점**할 수 있다. 실사용자 데이터로는 정답을 모르니 채점이 불가능하다.

## 3. 각본(Scenario) — 오늘 코드의 심장

```java
// src/main/java/com/scenelog/reaction/sim/Scenario.java
public record Scenario(
        long contentId,
        int durationSec,
        double baselinePerMinute,   // 배경 노이즈: 사용자당 분당 반응 횟수
        List<Peak> peaks            // ★ 심어둔 피크 = 정답지
) {
    public static Scenario defaultFor(long contentId, int durationSec) {
        int p1 = (int) (durationSec * 0.27);   // 27% 지점
        int p2 = (int) (durationSec * 0.68);   // 68% 지점
        return new Scenario(contentId, durationSec, 0.5, List.of(
                new Peak(p1, p1 + 50, ReactionType.TENSION, 15.0),
                new Peak(p2, p2 + 60, ReactionType.TOUCHED, 12.0)
        ));
    }
}
```

읽는 법: "이 영화의 27% 지점부터 50초간, 반응 확률이 평소의 **15배**가 된다(주로 TENSION)."

**생성 로직의 핵심 세 줄** (`ReactionSimulator.generate`):

```java
double p = scenario.baselinePerMinute() / 60.0;   // ① 기본: 초당 발생 확률 (노이즈)
if (active != null) p *= active.multiplier();     // ② 피크 안이면 확률을 15배로
if (rnd.nextDouble() >= p) continue;              // ③ 주사위 — 확률에 못 미치면 반응 없음
```

- **노이즈가 왜 필요한가**: 피크만 있으면 검출이 시험문제로서 너무 쉽다. 배경 잡음 위에서
  솟은 것을 찾아야 z-score가 의미 있는 일을 한다.
- **피크 안에서도 20%는 다른 반응** (`OFF_TYPE_RATIO = 0.2`): 실제 사람도 긴장 장면에서 웃는다.

### 결정적(deterministic) 생성 — seed의 의미

```java
Random rnd = new Random(seed);   // 같은 seed → 같은 난수 순서 → 같은 결과
```

`new Random(42)`는 "무작위처럼 보이지만 재현 가능한" 수열을 만든다. 그래서:
- 테스트가 안정적이다 (오늘 통과한 테스트는 내일도 통과)
- 시연이 재현 가능하다 (면접에서 돌려도 같은 그림)
- **멱등의 기반이 된다** (아래 §5)

## 4. 검증 5종 — 왜 하나하나가 필요한가

`ReactionService.registerBatch()`의 검증을 하나씩 뜯어본다. **각각이 실제 공격·실수 시나리오에 대응한다.**

| # | 검증 | 없으면 생기는 일 |
|---|---|---|
| 1 | 세션 존재 (404) | 유령 세션에 반응이 쌓여 집계가 오염 |
| 2 | **요청자 소유** (403) | 남의 시청 기록에 반응 조작 가능 — 데이터 신뢰성 붕괴 |
| 3 | offset ≤ 상영시간 (400) | 2시간 영화의 "9만 초 지점 반응" 같은 쓰레기 유입 |
| 4 | 배치 ≤ 500 (400) | 한 요청으로 수백만 건 밀어넣는 메모리 폭탄 |
| 5 | clientEventId 멱등 | 네트워크 재전송마다 반응이 2배씩 불어남 |

### 검증 2가 특별한 이유 — "애플리케이션이 FK를 대신한다"

```java
// ReactionService — 기획서 §5.4의 실물
WatchSession session = sessionRepository.findById(sessionId)
        .orElseThrow(() -> new ApiException(HttpStatus.NOT_FOUND, "세션을 찾을 수 없습니다..."));

if (!session.isOwnedBy(user.getUserId())) {
    throw new ApiException(HttpStatus.FORBIDDEN, "본인의 세션이 아닙니다");
}
```

`reaction_events`(MongoDB)의 `sessionId`는 PostgreSQL의 `watch_sessions`를 가리키지만,
**서로 다른 DB라 외래키(FK)로 보장할 방법이 없다.** PostgreSQL 안에서라면 DB가 거절해 줄 일을
여기서는 애플리케이션이 직접 해야 한다. **폴리글랏(DB 2개)의 대가를 갚는 지점**이며,
면접에서 "DB 두 개 쓰면 정합성은 어떻게 하나요?"의 답이 이 코드다.

### 검증 4·5는 코드가 아니라 선언으로

```java
// ReactionBatchRequest — 배치 상한은 DTO가 막는다
@NotEmpty @Size(max = 500, message = "배치는 최대 500건입니다")
List<@Valid Item> events
```

컨트롤러에 `if (events.size() > 500)`를 쓰지 않았다. `@Size` 선언이 컨트롤러 진입 **전에** 거른다.
enum 검증도 마찬가지 — `reactionType: "ANGRY"`는 JSON 역직렬화 단계에서 실패한다.
**검증을 앞 계층으로 밀수록 서비스 로직이 단순해진다.**

단, 역직렬화 실패는 기본적으로 500으로 새는 문제가 있어 핸들러를 추가했다:

```java
// GlobalExceptionHandler — 없는 enum 값이 500이 아니라 400이 되도록
@ExceptionHandler(HttpMessageNotReadableException.class)
public ResponseEntity<ErrorResponse> handleUnreadable(...) {
    return ResponseEntity.badRequest()
            .body(ErrorResponse.of(400, "요청 본문을 해석할 수 없습니다 (JSON 형식·enum 값 확인)"));
}
```

> **왜 400이어야 하나**: 500은 "서버 잘못", 400은 "요청 잘못"이다. 클라이언트가 틀린 값을 보낸 건
> 요청 잘못이므로 400. 상태코드를 정확히 나누는 것이 API 설계의 기본 예의다.

## 5. 멱등 — 오늘의 가장 중요한 개념

### 나쁜 예 vs 우리 코드

**😰 흔한 코드 — id를 서버가 무작위로:**
```java
event.setId(UUID.randomUUID().toString());   // 재전송하면? 새 UUID → 중복 저장됨
repository.save(event);
```
네트워크가 불안해 클라이언트가 같은 배치를 재전송하면 **반응이 2배로 불어난다.**
모바일 환경에서 재전송은 일상이다.

**✅ 우리 코드 — 결정적 id + 유니크 인덱스 + 중복은 조용히 스킵:**

```java
// ① ReactionSimulator — id가 내용에서 결정된다 (무작위가 아니다)
"sim-c%d-u%d-%d".formatted(scenario.contentId(), u, seq++)
// 같은 콘텐츠·같은 사용자·같은 순번이면 언제 만들어도 같은 id

// ② MongoIndexConfig — DB에 유니크 인덱스
indexOps.createIndex(new Index().named("client_event_id_uniq")
        .on("clientEventId", Sort.Direction.ASC).unique());

// ③ ReactionService — 중복이면 예외가 아니라 카운트
try {
    reactionEventRepository.save(new ReactionEvent(item.clientEventId(), ...));
    inserted++;
} catch (DuplicateKeyException e) {
    skipped++;   // 재전송된 이벤트 — 오류가 아니라 정상 (멱등)
}
```

세 조각이 합쳐져 오늘의 실측이 나왔다:

```
1차 실행: inserted=1883, skipped=0
2차 실행: inserted=0,    skipped=1883     ← 같은 요청을 다시 보내도 안전하다
```

> **응답을 보라**: 2차 실행이 에러가 아니다. `inserted=0`이 **정상 응답**이다.
> "이미 처리된 요청의 재시도"는 실패가 아니라 성공(아무것도 안 해도 됨)으로 취급한다 —
> 이것이 멱등 API의 핵심 사상이다.

## 6. 시연 모드 설계 — DB에 직접 넣지 않는 이유

**😰 편한 길:**
```java
// 시뮬레이터 결과를 Mongo에 바로 벌크 삽입 — 빠르다
mongoTemplate.insertAll(events);
```

**✅ 우리 코드 (`SimulateService`) — 실제 수집 경로를 통과시킨다:**
```java
ReactionBatchResponse r = reactionService.registerBatch(     // 실제 API와 같은 서비스 호출
        caller, realSessionId, new ReactionBatchRequest(new ArrayList<>(chunk)));
```

느린데 왜? **1,883건이 들어갔다는 사실 자체가 검증 5종이 실전에서 돌았다는 증거**가 되기 때문이다.
- 소유 검증을 통과하려면 → 진짜 세션을 만들어야 했고 (20개 생성)
- offset 검증을 통과하려면 → 각본이 상영시간 안에서만 생성해야 했고
- 멱등을 통과하려면 → id가 결정적이어야 했다

직접 삽입했다면 이 검증들은 "작성만 되고 한 번도 실행 안 된 코드"로 남았을 것이다.
**시연이 곧 통합 테스트다.** (단, day5의 100만 건 시드는 속도 때문에 의도적으로 벌크 경로를 쓴다 —
그때는 "검증을 우회했다"고 README에 명시한다. 같은 선택도 목적에 따라 답이 다르다.)

## 7. 인덱스를 코드로 만드는 이유 — 3호 사건의 교훈

**😰 편한 길 — 어노테이션 + 자동 생성 프로퍼티:**
```yaml
spring:
  mongodb:
    auto-index-creation: true   # 이 프로퍼티 이름이 맞는지 어떻게 확신하나?
```

우리는 바로 어제 **프로퍼티 이름이 조용히 무시되는 사고**(Boot 4 프리픽스 이동, 트러블슈팅 3호)를 겪었다.
인덱스는 day5 성능 실측의 대상이라 "있겠지"가 아니라 **있음이 보장**되어야 한다.

**✅ 우리 코드 (`MongoIndexConfig`) — 기동 시 코드로 생성:**
```java
@Bean
public ApplicationRunner mongoIndexInitializer(MongoTemplate mongoTemplate) {
    return args -> {
        var indexOps = mongoTemplate.indexOps(ReactionEvent.class);
        indexOps.createIndex(new Index().named("content_offset_idx")
                .on("contentId", Sort.Direction.ASC).on("offsetSec", Sort.Direction.ASC));
        indexOps.createIndex(new Index().named("client_event_id_uniq")
                .on("clientEventId", Sort.Direction.ASC).unique());
    };
}
```

코드는 무시되면 컴파일 에러거나 기동 실패다 — **조용히 사라지지 않는다.**
덤: day5에서 인덱스를 drop하고 측정한 뒤 앱을 재기동하면 자동 복구된다.

## 8. 오늘의 500 에러 — LazyInitializationException

시뮬레이션 첫 실행이 500으로 죽었다. JPA에서 가장 유명한 예외를 실전에서 만났다.

```
org.hibernate.LazyInitializationException: Could not initialize proxy [Content#1] - no session
	at com.scenelog.reaction.ReactionService.registerBatch(ReactionService.java:41)
```

### 원인 — 세 가지의 조합

```
① WatchSession.content = @ManyToOne(fetch = LAZY)   ← 콘텐츠는 "대역(프록시)"으로 온다
② open-in-view: false                                ← 요청 내내 DB 세션을 열어두지 않는다 (올바른 설정)
③ registerBatch에 @Transactional 없음                ← findById 후 트랜잭션이 바로 닫힘
```

```
[Tx 없음]  findById(sessionId)                        ← DB 세션 열렸다 즉시 닫힘
           session.getContent().getDurationSec()      ← 프록시: "이제 진짜 읽어야지" → 세션 없음 → 💥
```

### 해결 — OSIV를 켜는 게 아니라 경계를 명시한다

```java
@Transactional(readOnly = true)   // 메서드 전체가 하나의 DB 세션 안에서 실행된다
public ReactionBatchResponse registerBatch(User user, Long sessionId, ReactionBatchRequest request) {
```

`open-in-view: true`로 돌려도 예외는 사라진다. 하지만 그건 **신호를 끄는 것**이다:
- OSIV는 HTTP 응답이 끝날 때까지 DB 커넥션을 점유한다 → 커넥션 풀 고갈 위험
- "어디서 DB를 읽는지" 보이지 않게 된다 → N+1이 숨는다

**LazyInitializationException은 버그가 아니라 경계 알림이다** — "트랜잭션 밖에서 DB 접근이 일어났다"는
신호. 신호를 끄지 말고 경계를 바로잡는다. 상세: [트러블슈팅 4호](troubleshooting/2026-07-31-lazy-initialization.md)

## 9. 면접 예상 질문과 답

**Q1. "멱등성을 어떻게 구현하셨나요?"**
> 클라이언트가 이벤트마다 결정적인 id(clientEventId)를 부여하고, DB에 유니크 인덱스를 걸었습니다.
> 재전송된 이벤트는 DuplicateKeyException으로 감지해 오류가 아니라 skip으로 처리합니다.
> 실제로 같은 1,883건을 두 번 등록해 inserted=0을 확인했습니다.

**Q2. "DB가 두 개인데 참조 정합성은 어떻게 지키나요?"**
> MongoDB의 이벤트가 PostgreSQL의 세션을 가리키는데 FK를 걸 수 없어서, 쓰기 시점에
> 애플리케이션이 세션 존재·소유를 검증합니다. 그래도 새는 것에 대비해 주기적 고아 검출을
> 계획에 두었고, 실시간 차단이 아닌 사후 검출이라는 한계도 인지하고 있습니다.

**Q3. "시뮬레이터 데이터로 뭘 증명할 수 있죠? 가짜 데이터잖아요."**
> 두 가지입니다. 첫째, 수집·집계 파이프라인의 동작은 데이터 출처와 무관하게 증명됩니다.
> 둘째, 오히려 정답을 아는 데이터라서 검출 알고리즘을 채점할 수 있습니다 — 어디에 피크를
> 심었는지 아니까요. 실사용자 데이터로는 정답을 몰라 정확도를 측정할 수 없습니다.
> README에 시뮬레이터 사용을 명시해 숨기지 않았습니다.

**Q4. "OSIV(open-in-view)를 끄셨네요. 왜죠?"**
> 켜두면 HTTP 응답이 끝날 때까지 DB 커넥션을 점유해서, 외부 API 호출이 낀 요청에서
> 커넥션 풀 고갈의 원인이 됩니다. 끄면 LazyInitializationException이 나올 수 있지만,
> 그건 트랜잭션 경계가 잘못됐다는 신호라서 경계를 명시하는 쪽으로 해결했습니다.

## 10. 스스로 확인하기

1. 시뮬레이터가 만든 요청과 실제 버튼 클릭 요청을 서버가 구분할 수 있나? 그게 왜 중요한가?
