2. 시드 — 왜 벌크 경로를 따로 만들었나

나쁜 예 vs 우리 구조

😰 시연 모드(REST)로 100만 건 
요청당 검증 5종 + 문서 1건씩 save() → 100만 번 왕복 → 수 시간
✅ 시드 모드 — 측정용 데이터는 벌크로 
@Component
@Profile("seed")        // --spring.profiles.active=seed 로만 빈이 생긴다. 평소엔 없다
public class SeedRunner implements ApplicationRunner {
    // MongoTemplate.bulkOps(UNORDERED) 5,000건 배치 → 1,203,759건 / 129초

이 경로는 API 검증 5종을 우회한다. 숨기면 지적당하고, 밝히면 판단으로 읽힌다 — README에 명시한다: "성능 측정용 100만 건은 벌크 적재했고, API 검증은 시연 모드와 단위 테스트로 별도 검증했습니다."

우회해도 지키는 선 — 고아 이벤트 금지 (§5.4)

reaction_events의 sessionId는 PostgreSQL을 가리키지만 DB가 FK로 보장해 주지 않는다. 시드도 이 원칙을 깨지 않는다 — 세션 10,000행을 PostgreSQL에 실제로 만들고 그 진짜 sessionId를 이벤트에 넣는다. 시드 후에도 고아 검출 배치는 0건이어야 정상.

멱등 2겹

// ① clientEventId가 결정적: seed-c{contentId}-u{u}-{seq}
//    → 유니크 인덱스가 재적재를 막는다 (시연 데이터 sim- 과 프리픽스로 격리)
// ② 이벤트가 이미 있는 콘텐츠는 통째로 건너뛴다
//    → 재실행 시 세션 10,000행이 또 생기는 것까지 막는다
long existing = reactionEventRepository.countByContentId(contentId);
if (existing > 0) { log.info("... 건너뜀 (멱등)"); continue; }

②가 없으면 이벤트는 멱등이어도 세션은 실행마다 불어난다 — 멱등은 "모든 부수효과"에 대해 따져야 한다는 예시.

UNORDERED의 의미

mongoTemplate.bulkOps(BulkOperations.BulkMode.UNORDERED, ReactionEvent.class);
// ORDERED  : 앞 문서가 실패하면 뒤를 전부 중단 (순서 보장, 느림)
// UNORDERED: 실패해도 나머지를 계속 (병렬 가능, 빠름) — 중복 키(11000)만 세고 넘어간다

3. 인덱스 — 전화번호부 비유 ★

인덱스 없는 조회 = 이름순 정렬이 안 된 전화번호부

"김민준"을 찾으려면 첫 장부터 끝까지 다 넘겨야 한다. 몇 명이 나올지 모르니 중간에 멈출 수도 없다. 이것이 COLLSCAN(collection scan)이다:

totalDocsExamined : 1,205,642   ← 전화번호부 전체를 넘겼다
nReturned         : 239         ← 그중 김민준은 239명
executionTimeMillis: 7,041

필요한 게 0.02%여도 읽는 양은 100%. 그리고 이 비용은 데이터가 늘수록 조용히 자란다 — 1,883건일 때는 몇 ms라 보이지도 않았다.

인덱스 = 가나다순 정렬 + 색인

전화번호부가 가나다순이면 "ㄱ" 부근을 펴서 김민준만 읽고 끝낸다. 이것이 IXSCAN:

totalKeysExamined : 239         ← 색인에서 239개만 짚고
totalDocsExamined : 239         ← 그 239건만 실제로 읽었다
executionTimeMillis: 202

내부 구조는 B-트리

                [ contentId 25 ]
               /                \
      [ 2 .. 24 ]              [ 26 .. 51 ]
      /    |    \              /    |     \
   리프: (2,0) (2,3) (2,7) ... → 정렬된 (contentId, offsetSec) 쌍 + 문서 위치
  • 항상 정렬 상태를 유지하는 트리 → 원하는 키까지 몇 번의 분기로 도달 (수백만 건이어도 3~4단)
  • 리프가 정렬돼 있으므로 범위 조회(offsetSec 2400~2500)는 시작점 찾고 옆으로 읽으면 끝
  • 그래서 복합 인덱스는 (등호로 찍는 필드, 범위로 훑는 필드) 순서로 만든다 — (contentId, offsetSec)

왼쪽 접두사 (leftmost prefix) — 인덱스 하나가 두 쿼리를 커버

인덱스: (contentId, offsetSec)

쿼리 A: {contentId: 2, offsetSec: 2400~2500}  → 인덱스 완전 사용
쿼리 B: {contentId: 2}                         → 왼쪽 접두사만 사용, 역시 인덱스를 탄다 ✅
쿼리 C: {offsetSec: 2400~2500}                 → 왼쪽(contentId)이 없다 → 인덱스 못 탄다 ❌

전화번호부 비유로: 가나다순 전화번호부에서 "성이 김씨인 사람"(B)은 찾기 쉽지만, "이름이 민준인 사람"(C)은 성을 모르면 결국 전부 넘겨야 한다. 우리 집계 쿼리 findByContentId가 B다 — offsetSec 조건이 없어도 같은 인덱스를 탄다.

쓰기 비용 — 인덱스는 공짜가 아니다

인덱스는 "정렬 상태 유지"를 쓰기 시점마다 지불한다. 문서 1건 삽입 = 컬렉션 쓰기 + 인덱스마다 B-트리 갱신. 인덱스가 3개면 쓰기 1번이 사실상 4번의 갱신이다.

우리 실측에서도: 시드 129초는 인덱스 2개(복합+유니크)를 유지하며 넣은 시간이다. 그래서 "조회가 실제로 쓰는 인덱스만 만든다"가 원칙 — 안 쓰는 인덱스는 조회는 못 돕고 쓰기만 늦춘다.

4. explain 읽는 법 — 성능 주장의 근거 문서

db.reaction_events.find({contentId: 2, offsetSec: {$gte: 2400, $lt: 2500}})
  .explain("executionStats")
필드뜻건강한 상태

totalDocsExamined실제로 읽은 문서 수nReturned에 가까울수록 좋다
nReturned조건에 맞아 반환된 수—

한 줄 요약: examined ≈ returned이면 인덱스가 일하고 있고, examined ≫ returned이면 낭비다.
우리 측정: 1,205,642 → 239 (5,044배 낭비) vs 239 → 239 (낭비 0).

5. 인덱스가 만능이 아니라는 것도 숫자로

explain은 35배 빨라졌는데 집계 API는 왜 3배만 빨라졌나?

집계 API 총 비용 = (관계없는 118만 건 스캔: ~4초)  ← 인덱스가 없앤 부분
                + (필요한 23,325건 fetch + 집계 계산 + PostgreSQL 저장: ~2초)  ← 그대로 남는 부분

인덱스는 "찾기"를 없애 주지, "가져와서 처리하기"는 못 없앤다. 남은 2초를 줄이려면 증분 집계(전량 재계산 포기)라는 다른 종류의 트레이드오프가 필요하다 — README 한계 절 기록.

반대편 증거 — 작은 테이블엔 인덱스가 필요 없다

Seq Scan on segment_stats ... rows=870 ... Execution Time: 0.468 ms

segment_stats(마트, 1,690행)는 PostgreSQL 플래너가 일부러 Seq Scan을 고른다 — 전부 읽는 게 색인을 오가는 것보다 싸기 때문. 인덱스는 데이터가 커야 이긴다.
원본(120만)은 인덱스 필수, 집계가 미리 줄인 마트(1,690)는 스캔이 더 쌈 — fact/mart 분리(day4)가 조회 경로에서 값을 하는 순간이다.

6. 장애 주입 — 의도적으로 부수고 관찰하기 (우대 2)

docker stop scenelog-mongo   → 집계 API 호출

관찰된 타임라인:

즉시    : MongoNodeIsRecoveringException (code 11600, InterruptedAtShutdown) — 드라이버가 감지
0~30초  : "Waiting for server to become available... Remaining time: 29996 ms" — 재연결 대기
30초    : MongoTimeoutException → DataAccessResourceFailureException → 500
복구 후  : docker start → 앱 재시작 없이 다음 요청부터 자동 재연결 (2,001ms 정상 응답)

배운 것 2가지:

  1. 드라이버는 생각보다 똑똑하다 — 죽음을 즉시 감지하고, 30초간 재연결을 시도하고, 살아나면 스스로 붙는다. 앱 재시작이 필요 없었다.
  2. 사용자는 에러보다 30초 무응답을 먼저 겪는다 — serverSelectionTimeout 기본 30초는 API 응답으로는 너무 길다. 빠른 실패가 필요하면 serverSelectionTimeoutMS를 낮춘다 (에러를 빨리 주는 것도 설계다).

7. 측정 설계에서 배운 것 — 계획과 실제가 달랐던 두 곳

① "인덱스 드랍 → 시드" 순서가 실효가 없었다.
MongoIndexConfig가 앱 기동 시마다 인덱스를 재생성한다(day3에 코드로 못박은 설계). 시드도 앱이므로 드랍해 둬도 시드 기동 순간 되살아난다. → 시드는 인덱스 있는 채로 넣고, 드랍은 서빙 앱이 뜬 뒤에 했다 (앱은 기동 시에만 만드니 드랍이 유지된다). 자동 복구 장치가 있으면 "꺼진 상태"를 만드는 절차도 그에 맞춰 달라진다.

② 타임라인 API는 측정 대상이 아니었다.
계획서는 타임라인 API p50/p95를 재라고 했지만, 타임라인은 PostgreSQL(segment_stats)+Redis만 읽는다 — Mongo 인덱스와 무관하다. Mongo를 실제로 타는 경로는 집계 API (findByContentId, 왼쪽 접두사)다. 측정 전에 "이 요청이 정확히 어떤 쿼리를 내는가"부터 확인해야 한다 — 안 그러면 인덱스와 무관한 숫자를 인덱스 성과로 착각한다.

8. 면접 예상 질문과 답

Q1. "인덱스를 추가하면 왜 빨라지나요?"

인덱스가 없으면 조건에 맞는 문서를 찾으려고 컬렉션 전체를 읽습니다(COLLSCAN). 실측으로 120만 건 중 239건을 찾는 데 전부를 읽어 7초가 걸렸습니다. (contentId, offsetSec) 복합 인덱스는 B-트리로 정렬을 유지하므로 239건만 짚어 0.2초 — 스캔량이 5천분의 1로 줄었습니다.

Q2. "인덱스의 비용은 없나요?"

쓰기마다 B-트리 갱신 비용을 냅니다. 인덱스가 많을수록 삽입이 느려지고 저장 공간도 씁니다. 그래서 조회가 실제로 타는 인덱스만 만들었고, 복합 인덱스의 왼쪽 접두사 규칙으로 인덱스 하나가 범위 조회와 콘텐츠 전체 조회를 모두 커버하게 했습니다.

Q3. "인덱스를 넣었는데 API가 35배가 아니라 3배만 빨라진 이유는?"

인덱스는 '무관한 데이터를 읽는 비용'만 없앱니다. 집계는 대상 콘텐츠의 2.3만 건을 어차피 가져와 계산·저장해야 하고 그 비용(~2초)은 남습니다. 더 줄이려면 인덱스가 아니라 증분 집계로의 전환이 필요하다는 한계를 문서에 남겼습니다.

Q4. "100만 건은 어떻게 만들었나요? 실데이터가 아닌데 의미가 있나요?"

별도 프로파일의 벌크 적재기로 129초에 넣었습니다. API 검증을 우회하는 경로라 README에 명시했고, 정합성 원칙(고아 이벤트 금지)은 지켰습니다 — 세션 1만 행을 PostgreSQL에 실제로 만들어 참조하게 했습니다. 인덱스 유무의 스캔량 차이는 데이터가 합성이어도 동일하게 성립합니다.

Q5. "장애가 나면 어떻게 되나요?"

Mongo를 의도적으로 내려 봤습니다. 드라이버가 즉시 감지하고 30초 재연결을 시도한 뒤 타임아웃 예외가 500으로 번역됩니다. 재기동하면 앱 재시작 없이 자동 재연결됩니다. 기본 30초 대기가 사용자에겐 무응답으로 보인다는 점을 확인했고, 빠른 실패가 필요하면 serverSelectionTimeoutMS를 낮추는 선택지를 기록했습니다.
