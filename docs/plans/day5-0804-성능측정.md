# 8/4 — 대량 시드 + 인덱스 실측 + 트러블슈팅 로그

> **코드를 만드는 날이 아니라 숫자를 만드는 날이다.**
> 이력서에 쓸 "p95 800ms → 30ms" 같은 문장이 오늘 나온다.

## 목표

데이터를 100만 건 규모로 불려서, **인덱스가 있을 때와 없을 때의 차이를 실제로 측정**한다.

## 산출물

- [ ] `reaction_events` 약 100만 건 (부담 시 30만)
- [ ] 인덱스 **없을 때** 실행계획·응답시간 기록
- [ ] 인덱스 **있을 때** 실행계획·응답시간 기록
- [ ] **§11 정량 성과 1번 확보** ← 오늘의 핵심
- [ ] 트러블슈팅 로그 2~3건 작성
- [ ] 단위 테스트 전체 통과

## 작업 순서

### 1단계 — 시드 모드 (`reaction/sim/SeedRunner.java`)

시연 모드(REST)로 100만 건을 보내면 수 시간이 걸린다. **벌크 적재 경로를 따로 만든다.**

```
콘텐츠 50편 × 세션 200 × 세션당 약 100건 ≈ 100만 건
```

- `MongoTemplate`의 `bulkOps(BulkMode.UNORDERED)` 사용
- `--spring.profiles.active=seed`로만 실행되게 분리 (`@Profile("seed")`)

> ⚠️ **이 경로는 API 검증 5종을 우회한다.** 의도된 트레이드오프이므로 **README에 반드시 밝힌다**:
> "성능 측정용 100만 건은 벌크 적재했고, API 검증은 시연 모드와 단위 테스트로 별도 검증했습니다."
> 숨기면 지적당하고, 밝히면 판단으로 읽힌다.

### 2단계 — 인덱스 없이 측정

```javascript
// mongosh
db.reaction_events.dropIndex("contentId_1_offsetSec_1")
db.reaction_events.find({contentId: 1, offsetSec: {$gte: 2400, $lt: 2500}})
  .explain("executionStats")
```

기록할 것: `totalDocsExamined` · `nReturned` · `executionTimeMillis`

### 3단계 — 인덱스 만들고 재측정

```javascript
db.reaction_events.createIndex({contentId: 1, offsetSec: 1})
// 같은 쿼리 다시 explain
```

기록할 것: `totalKeysExamined` · `totalDocsExamined` · `executionTimeMillis`

### 4단계 — API 응답시간 p50/p95

단일 측정값은 노이즈다. **20회 반복**해서 분포를 본다.

```powershell
$times = 1..20 | ForEach-Object {
    (Measure-Command { Invoke-WebRequest "http://localhost:8080/api/contents/1/timeline" -UseBasicParsing }).TotalMilliseconds
}
$sorted = $times | Sort-Object
"p50: $($sorted[9]) ms"
"p95: $($sorted[18]) ms"
```

> 캐시가 켜져 있으면 두 번째부터는 캐시 값을 읽는다. **캐시 껐을 때/켰을 때를 나눠 측정하면 캐시 효과도 숫자가 된다.**

### 5단계 — PostgreSQL 쪽도 (선택)

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM segment_stats WHERE content_id = 1 ORDER BY bucket_start_sec;
```
`Seq Scan` → `Index Scan` 전환을 확인한다.

### 6단계 — 트러블슈팅 로그 작성

`docs/troubleshooting/`에 이 형식으로:

```
이슈: 타임라인 조회가 N초 소요
원인: 로그/explain 확인 → 반응 100만 건을 전부 스캔 (totalDocsExamined 1,000,000 / nReturned 3,200)
대응: (contentId, offsetSec) 복합 인덱스 추가
결과: p95 ___ms → ___ms, 스캔 1,000,000 → 3,200
재발 방지: 신규 조회 경로 추가 시 explain 확인을 PR 체크리스트에 포함
```

### 7단계 — 의도적 장애 주입 (우대사항 2)

```
docker stop scenelog-mongo
→ 반응 등록 API 호출 → 실패
→ 로그에서 원인 확인 → 기록
docker start scenelog-mongo
```

"실사용 서비스 장애 대응 경험"의 대체 증거가 된다.

## 🚨 손절 기준

| 상황 | 대응 |
|---|---|
| 100만 건 적재가 오래 걸림 | 30만으로 낮춘다. **그 이하는 인덱스 효과가 노이즈에 묻혀 무의미** |
| 인덱스 차이가 안 남 | 데이터가 너무 적거나 쿼리가 인덱스를 안 타는 것. `explain`의 `stage`를 확인 (`COLLSCAN` vs `IXSCAN`) |
| 측정이 반나절 초과 | 인덱스 실측 1건만 확보하고 나머지는 포기. **숫자 1개라도 있는 게 0개보다 압도적으로 낫다** |
