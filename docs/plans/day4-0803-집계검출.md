### 3단계 — 집계 서비스 (`analytics/AggregationService.java`)

```
1. MongoDB에서 해당 content의 reaction_events 전부 조회
2. Aggregator.aggregate(events, 10) → Map<버킷시작초, BucketCounts>
3. segment_stats에 UPSERT (전량 재계산 후 덮어쓰기)
4. 그 결과로 HighlightDetector.detect() → highlights 저장 (기존 것 삭제 후 재삽입)
5. Redis에서 해당 content의 타임라인 캐시 삭제 (무효화)
```

**멱등의 실현 방식**: 증분 누적이 아니라 **전량 재계산 + 덮어쓰기**다.
JPA `save()`는 PK가 있으면 UPDATE가 되므로 자연스럽게 UPSERT가 된다.
한계(데이터가 커지면 비효율)는 README에 기록한다 — **한계를 아는 것이 어필이다.**

### 4단계 — 조회 + 캐시 (`analytics/TimelineService.java`)

`GET /api/contents/{id}/timeline?bucket=10`

```java
@Cacheable(value = "timeline", key = "#contentId")     // 조회 시 캐시
@CacheEvict(value = "timeline", key = "#contentId")    // 집계 후 무효화
```

`@EnableCaching` + `RedisCacheManager` 설정이 필요하다 (`common/config/RedisConfig.java`).

> **무효화가 캐시의 핵심이다.** 없으면 집계가 갱신됐는데도 옛 데이터를 계속 보여준다.
> 면접에서 "캐시 쓰셨네요, 무효화는요?"가 반드시 나온다.

### 5단계 — 검출 트리거 API
`POST /api/admin/contents/{contentId}/aggregate` (ROLE_ADMIN) — 집계 + 검출을 한 번에.

## 검증

```
docker exec scenelog-postgres psql -U scenelog -d scenelog -c "SELECT * FROM segment_stats WHERE content_id=1 ORDER BY total_count DESC LIMIT 5;"
docker exec scenelog-postgres psql -U scenelog -d scenelog -c "SELECT * FROM highlights WHERE content_id=1;"
docker exec scenelog-redis redis-cli KEYS "*timeline*"
```

**멱등 확인**: aggregate를 두 번 호출 → `segment_stats` 행 수와 값이 동일해야 한다.
**캐시 확인**: timeline 조회 후 redis에 키 생성 → aggregate 실행 후 키 사라짐.

## 🚨 손절 기준

| 상황 | 대응 |
|---|---|
| Redis 캐시가 막힘 | 캐시를 8/6으로 이월. **집계·검출이 캐시보다 중요하다** |
| 복합 PK 매핑이 막힘 | 단일 PK(`BIGSERIAL`) + `(content_id, bucket_start_sec)` unique 제약으로 대체 |
| 검출 결과가 정답과 안 맞음 | 임계값(`Z_THRESHOLD`)을 조정하고 **조정 과정을 기록한다.** 이게 EDA 근거가 된다 |
